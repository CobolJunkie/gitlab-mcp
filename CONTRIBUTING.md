# Contributing

Contributions are welcome through GitLab issues and merge requests.

Read [docs/DEVELOPER_GUIDE.md](docs/DEVELOPER_GUIDE.md) for the architecture,
tool lifecycle, security invariants, test map, and documentation expectations.

## Development workflow

1. Create or reference an issue for non-trivial changes.
2. Branch from the latest `main`; use a focused branch and conventional commit
   message.
3. Install with `npm ci`.
4. Update tests, `docs/gitlab-tool-contracts.json`, and documentation when
   behavior changes. The MCP bundle is generated by build/release validation
   and is not committed. If shared distribution metadata changes, update
   `distribution.json` and run `npm run adapters:generate` before verification.
5. Run:

   ```text
   npm run check
   npm run lint
   npm run format:check
   npm run deps:check
   npm test
   npm run test:coverage
   npm run adapters:check
   npm run check:versions
   npm run check:bundle
   npm audit --omit=dev
   npm run build
   npm run smoke
   npm run validate:harnesses
   npm run release:validate
   ```

6. Open a draft merge request, describe security or compatibility effects, and
   mark it ready only after its pipeline succeeds.

Never include tokens, private repository data, job logs containing secrets, or
real customer payloads in fixtures. New tools must have explicit safety
annotations and exact route-contract coverage.

For a release candidate, also run `npm run test:integration:disposable` only
with a dedicated disposable GitLab project and the variables documented in
`docs/CONFIGURATION.md`; it deliberately skips when those credentials are not
available.
